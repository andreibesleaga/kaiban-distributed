# kaiban-distributed — v2.1 Roadmap (post-2.0 plan)

> **Status: PLAN (not implemented).** Saved for a later version. v2.0 ships the items in
> `KAIBAN-v2.0-MASTER-PLAN.md`; this document captures the next tranche deferred during BETA.3.
> Authoritative invariants/NFRs still apply (master plan §B1). Everything here stays **opt-in /
> default-OFF** (invariant #8) and additive (no breaking change to the 5 canonical channels without an ADR).

Three workstreams:
1. **Federation-egress enforcement** — extend the Action Gate to outbound A2A / MCP traffic.
2. **Default-wire the fleet cost limiter** — make economics enforcement turnkey (Redis-backed) without
   forcing each consumer to inject a limiter.
3. **Universal agent messaging schema** — a driver-agnostic, schema-enforced envelope for ALL agent
   pub/sub (Kafka, Redis, BullMQ, future AMQP), with a flexible payload per message type. **(centerpiece)**

---

## 1. Federation-egress enforcement (ADR-022, planned)

**Today (v2.0):** the Action Gate (`src/governance/action-gate.ts`) is enforced on the **inbound** task
hot path (`AgentActor` pre-execution guard, ADR-021). **Outbound** federation — the gateway dispatching
A2A `message/send` (`KaibanAgentExecutor`) and the MCP server's `dispatch_task` — is NOT yet gated.

**Goal:** every *outbound* / cross-boundary action also passes the gate, so policy / kill-switch / cost
apply symmetrically to what agents emit, not just what they receive.

**Design (additive, default-OFF):**
- Introduce an `EgressGate` adapter (reusing `IAdmissionGate` / `buildAdmissionGate`) that wraps the
  same `ActionGate`. Operations: `outbound-message` (A2A) and `tool-call` (MCP `dispatch_task`).
- **A2A:** in `KaibanAgentExecutor.execute` (`a2a-executor.ts`), call the gate **before** publishing to
  the agent mailbox; a `block`/`terminate` becomes a terminal A2A `rejected` task (no publish), `degrade`
  annotates the task. Reuses the existing `validateTaskInput` path.
- **MCP:** in the `dispatch_task` tool handler (`mcp-server.ts`), call the gate before `deps.dispatchTask`
  — composes with (does not replace) the existing elicitation consent gate.
- Wire via the gateway composition (`main/gateway.ts`) behind `GOVERNANCE_ENABLED`, sharing one
  `ActionGate` + `AuditLog` instance with the worker config.
- **Checks:** gate block→A2A `rejected` / MCP error result (no side effect); audit records the egress
  decision; default-OFF preserves current behavior; A2A + MCP conformance suites stay green.

## 2. Default-wire the fleet cost limiter (ADR-023, planned)

**Today (v2.0):** `CostReservation` / `RateCostLimiter` exist and are 100%-tested; the worker admission
gate adds cost enforcement **only when a `CostLimiterPort` is injected** (`buildWorkerAdmissionGate`), so
out-of-the-box `ECONOMICS_ENABLED` does not yet enforce a *fleet* budget — by design, to avoid forcing a
Redis client into every node and to keep budgets fleet-wide rather than per-node.

**Goal:** when `ECONOMICS_ENABLED=true`, the worker automatically builds a **Redis-backed**
`RateCostLimiter` (shared fleet state) and composes it into the admission gate — turnkey fleet cost
control — while keeping a `RateLimiterMemory` fallback for single-node / test.

**Design (additive, default-OFF):**
- A `buildFleetCostLimiter(economics, { redisUrl, redisTls })` factory in `src/shared` returning a
  `RateCostLimiter` whose `RateLimiterFactory` constructs `RateLimiterRedis({ storeClient, … })` (shared
  ioredis client; reuses the node's existing Redis config + TLS). Memory fallback when `redisUrl` absent.
- `buildSecurityDeps` / `agent-node.ts` pass it into `buildWorkerAdmissionGate` when `ECONOMICS_ENABLED`.
- Lifecycle: the limiter's Redis client joins the node's graceful-shutdown step list.
- **Decisions to settle:** cost-unit definition (micro-USD vs tokens) and where the per-step
  `estimatedCostUnits` comes from (model pricing table via `cache-accounting` / `model-router` →
  `GateContext.estimatedCostUnits`). Likely a small `estimateCost(payload, pricing)` helper.
- **Checks:** two nodes share one budget (fleet-wide reservation/compensation across processes, real
  Redis e2e); disabled ⇒ no limiter, no Redis client; per-task accounting unchanged (§B1.3 COST guard).

## 3. Universal agent messaging schema (ADR-024, planned) — **centerpiece**

### Problem
Agents publish to several backends (Redis Pub/Sub, BullMQ/Redis streams, Kafka; future AMQP) over the 5
canonical channels. Today the wire shape is the internal `MessagePayload`
(`{ taskId, agentId, data, timestamp, traceHeaders? }`) — adequate, but **not a formally-specified,
versioned, schema-enforced contract**, and not described in a machine-readable, tooling-friendly way. We
want ONE generic, driver-agnostic envelope that any agent (any specialization, any framework) can publish
and any consumer can validate, **with the body staying flexible** per message type / task.

### Research outcome (industry standards, verified 2026)
- **CloudEvents 1.0.2 (CNCF)** — a *protocol-agnostic* event **envelope**: standard metadata attributes
  (`id`, `source`, `type`, `specversion`, `time`, `subject`, `datacontenttype`, `dataschema`, + named
  **extension attributes**) wrapping a flexible `data` payload. Has official **bindings** for Kafka
  (structured + binary content modes; non-data attributes → `ce_`-prefixed headers), AMQP, MQTT, NATS,
  HTTP, WebSockets. This is exactly the "generic header + message" the envelope needs.
- **AsyncAPI 3.x** — the "**OpenAPI for event-driven / message-driven APIs**": one YAML/JSON document
  describing every **channel**, **message**, **payload schema** (AsyncAPI Schema = JSON-Schema superset,
  or **Avro**), **operation** (send/receive), **server**, and **protocol binding** (Kafka/AMQP/MQTT/NATS/
  WS). This is the *contract & enforcement spec* layer + a tooling/codegen/validation ecosystem.
- **Schema enforcement** — JSON Schema (default; matches our `zod` + `fast-check` stack) or Avro/Protobuf
  via a **Schema Registry** (Confluent-compatible) for Kafka; for Redis/BullMQ we validate in-process at
  publish/consume.

### Proposed design: a CloudEvents envelope, an AsyncAPI contract, driver-agnostic enforcement
**(a) The envelope — CloudEvents-aligned `KaibanEvent`** (supersedes the raw `MessagePayload` on the wire;
`MessagePayload` becomes the `data` body):
```jsonc
{
  "specversion": "1.0",
  "id": "<uuid>",                         // unique event id
  "source": "kaiban/agent/<agentId>",      // producer
  "type": "com.kaiban.task.dispatch",      // versioned event type (registry key)
  "time": "2026-…Z",
  "datacontenttype": "application/json",
  "dataschema": "kaiban://schemas/task.dispatch/1",  // → schema registry entry
  // kaiban extension attributes (CloudEvents extensions — flat, string-ish):
  "taskid": "<taskId>",                    // dedup key (invariant: AP+BASE)
  "agentid": "<targetAgentId>",
  "tenantid": "<tenant>",                  // optional
  "traceparent": "…", "tracestate": "…",   // W3C trace context (replaces traceHeaders)
  // flexible, per-type body — validated against `dataschema`:
  "data": { /* task/message/state-event payload, specialization-specific */ }
}
```
**(b) The contract — `asyncapi.yaml`** describing the 5 canonical channels
(`kaiban-agents-{id}`, `kaiban-events-completed`, `kaiban-events-failed`, `kaiban-state-events`,
`kaiban-hitl-decisions`), each message = the `KaibanEvent` envelope with a per-`type` payload schema, plus
Kafka/Redis bindings. Generated docs + types; lints in CI (AsyncAPI CLI validator).
**(c) Enforcement — a schema layer in the Messaging Abstraction Layer (MAL):**
- A `SchemaRegistry` (start with an in-repo JSON-Schema map keyed by `type`+version; Confluent-registry
  adapter optional for Kafka) + an `EnvelopeCodec` that wraps/validates on `publish` and parses/validates
  on `subscribe`, in **every** driver (BullMQ/Kafka/AMQP) — so enforcement is uniform regardless of
  `MESSAGING_DRIVER`. Invalid envelope/payload → reject before publish (mirrors `A2A_INPUT_CAPS`), or
  route to DLQ on consume (`schema_violation`).
- **Backward-compatible migration:** a transitional decoder accepts both raw `MessagePayload` and the new
  `KaibanEvent` (detect `specversion`), so a mixed fleet interoperates during rollout; envelope becomes
  mandatory in a later major. Body stays flexible — only the envelope + the named `type`'s schema are
  enforced.
- **Versioning & evolution:** `type` carries a version suffix; schema changes follow compat rules
  (backward/forward) per `event-governance` skill; registry is the source of truth.

### Why this shape
- **Generic + flexible:** CloudEvents standardizes only the envelope; `data` is whatever the agent's
  specialization/task needs — enforced *per `type`*, not globally.
- **Driver-agnostic:** CloudEvents has bindings for every backend we use/plan; the MAL codec hides the
  per-driver header/value mapping (Kafka `ce_` headers vs Redis JSON).
- **Tooling:** AsyncAPI gives machine-readable docs, codegen, contract tests, and the "Kafka-OpenAPI"
  experience the maintainer asked for; JSON Schema reuses our existing `zod`/`fast-check` validation.
- **Interop:** CloudEvents/AsyncAPI are CNCF/Linux-Foundation standards → external agents & tools can
  speak our channels without bespoke glue; complements A2A (front door) + MCP (tool surface).

### Phased delivery (v2.1)
- **M-Schema.1** — define `KaibanEvent` (CloudEvents) types + the in-repo JSON-Schema registry +
  `EnvelopeCodec` (publish/consume validation) as a MAL add-on; **off by default** behind
  `MESSAGING_SCHEMA_ENFORCED`. Transitional dual-decoder. 100% cov.
- **M-Schema.2** — author `asyncapi.yaml` for the 5 channels + CI lint (AsyncAPI CLI) + generated docs.
- **M-Schema.3** — Kafka Schema-Registry adapter (Confluent-compatible) + structured/binary content-mode
  mapping; Redis/BullMQ in-process validation; `schema_violation` DLQ taxonomy entry.
- **M-Schema.4** — flip enforcement on by default in a later **major** (with MIGRATION); keep the
  dual-decoder one version for rollout.

### Risks / decisions to settle first
- Changing the wire envelope touches the **messaging-channel contract** → requires an ADR + careful
  migration (§6 forbidden-actions / §B1.2). Dual-decoder + default-off de-risks rollout.
- Cost-unit + pricing source overlaps with workstream 2 — settle once.
- Avro-vs-JSON-Schema default: start JSON Schema (matches `zod`); offer Avro for Kafka-registry users.

> change to the 5 canonical channels without an ADR). Verified against the v2.0 (`feat/v2.0`) code.

### CR-1. A2A forward-compat — advertised-but-not-served / flagged-only (Phase A finish)
The v2.0 A2A surface is stable v0.3 with a v1.0 seam; several "Phase A" forward-compat items are
declared on the AgentCard (the seam) but not yet implemented behind it:
- **gRPC transport** — advertised in `additionalInterfaces` (`a2a-agent-card.ts`, `${baseUrl}/a2a/grpc`)
  but **only JSON-RPC at `/a2a/rpc` is actually served**; no gRPC server. → implement the gRPC binding.
- **Push-notification webhooks** — the `pushNotifications` capability flag is wired end-to-end, but
  there is **no webhook delivery** implementation. → implement delivery + signing.
- **Signed-AgentCard (JWS) verify** — **absent**; the card is plain JSON (JWT request-auth is separate).
  → add JWS card signing + verification (flagged).
- **Lifecycle states `input-required` / `auth-required`** — **absent** (only `rejected` of the extended
  set is emitted, alongside `submitted/working/completed/failed/canceled`). → add the remaining states.

### CR-2. Resilience (Phase R) — supervision & loop-guard completeness
- **Auto-revival supervisor with backoff+jitter** — **absent** as code; v2.0 resilience leans on message
  durability + let-it-crash + checkpoint/resume + platform (k8s) restart. → add an in-process supervised
  auto-revival path (actor-revival only) with backoff+jitter.
- **Loop-termination guards** — iteration cap (`maxIterations`) and token-budget cap are present, but
  **wall-clock cap and oscillation detection are absent**. → add wall-clock + oscillation/handoff guards.
- **Circuit-breaker half-open** — `SlidingWindowBreaker` recovers by window expiry (auto-close), which is
  an improvement over the old time-only behavior, but it is **not a classic single-probe HALF_OPEN trial
  gate**. → add a true half-open probe if stricter recovery semantics are wanted.

### CR-3. Governance (Phase G) — provenance-check as an Action-Gate validator
The Action Gate ships firewall / breaker / cost / policy-as-code / kill-switch validators, and a
hash-chained audit log. A **dedicated provenance-check `GateValidator` is absent** — provenance/trust
lives only in the memory layer (`SecureMemoryStore` `MemoryProvenance` / trust floor), not as a gate
validator. → add a provenance validator (it is also the foundation the anti-hallucination harness below
builds on). Relatedly, federation **egress** gating remains deferred — see §1 above.

## 4. Governance findings from the external evaluation package (added 2026-08-23)

Source: `sustainability-loop-eval` v1.1.0 (github.com/andreibesleaga/sustainability-loop-eval, Zenodo
concept DOI 10.5281/zenodo.22056633), which runs architecture fitness functions through the shipped
`ActionGate` / `AuditLog` of `kaiban-distributed@2.0.0` (npm) at commit `17ad362`. Governance unit suite
71/71 and e2e 69/69 (real Redis) reproduced there. Items below are defects or gaps it surfaced; all stay
opt-in / default-OFF and additive.

### 4.1 DEFECT — off-ladder verdict can mask `terminate` (fix in v2.1, fail-closed)
`src/governance/action-gate.ts` aggregates by sorting on `GATE_ACTION_SEVERITY[verdict.action]`. An action
that is not in `GateAction` has no entry → the comparator returns `NaN` → the sort is not total and the
decision collapses to insertion order. Measured: verdicts `[allow, "not-a-rung", terminate]` → gate decision
**`allow`**; a lone rogue validator returning `"not-a-rung"` is returned verbatim. A malformed validator can
therefore outrank the kill-switch.
**Fix:** before aggregation, map any action not in the ladder to `block` (fail closed, same posture as a
throwing validator), keep the raw value in the verdict `reason`, and add unit cases: rogue-alone ⇒ `block`;
rogue + `terminate` ⇒ `terminate`; rogue + `allow` ⇒ `block`. Also export a `isGateAction()` guard.

### 4.2 GAP — the five rungs have one meaning upstream (documentation + optional human port)
In the default actor path (`shared/admission-gate.ts`) `allow`/`degrade` proceed and `escalate`/`block`/
`terminate` are treated identically (dead-letter); `degrade` degrades nothing; there is no human-approval
port; `block` vs `terminate` is undocumented (only the registry distinguishes them: revoked ⇒ `terminate`,
other inactive ⇒ `block`). The evaluation package had to define the semantics itself:
allow = run · degrade = run reduced / defer · escalate = run only with human approval · block = withheld,
human may authorise a reduced/deferred fallback only · terminate = never runs, not overridable.
**Plan:** (a) document the rung semantics and the block/terminate distinction in `docs/governance/
GOVERNANCE.md`; (b) add an optional `HumanApprovalPort` (pending-decision queue + callback, default-OFF)
consulted by the admission gate for `escalate`/`block`; `terminate` is never routed to it; (c) wire
`degrade` to `routeModel` (currently exported, never invoked) behind a flag.

### 4.3 GAP — audit log is tamper-evident for edits, not for truncation
`AuditLog.verify()` recomputes hashes but has no length/tip commitment, so tail truncation, deletion and
reordering of the last records verify as valid; `records()` returns the live internal array (callers can
mutate it). **Plan:** `anchor(): {length, tipHash}` + `verify(anchor?)`; return a frozen copy from
`records()` (or document that it is live); unit cases for truncation/deletion/reorder.

### 4.4 GAP — deferred / paused tasks have no governance notion
A verdict taken "now" that is executed later (deferral) is currently outside the gate's vocabulary; the
evaluation package gates once on arrival and executes later on that audited decision. **Plan:** record
`executedAt` on the audit record when actuation happens (separate from the decision timestamp), and point
a future pause/rehydrate of deferred work at the existing `WorkflowOrchestrator` checkpoint→resume
(`CheckpointStore`) — it is the natural place, and it is unrelated to governance today.

### 4.5 PACKAGING — export a `./governance` subpath
Importing the package root (`dist/src/index.js`) eagerly loads ~249 packages (LangChain, OTel
instrumentations, express, socket.io, ioredis, bullmq, kafkajs…). Consumers that only want the gate pay
the whole tree and inherit its advisories (21 `npm audit` findings on 2026-08-22, all transitive via
kaibanjs → LangChain/langsmith/OTel/uuid/fast-xml-parser). **Plan:** add `"./governance"` to `exports`
(gate, audit-log, policy-engine, registry, types only), and bump kaibanjs / LangChain to clear the
advisories.

## 5. The five rungs as agentic controls — semantics to adopt upstream (added 2026-08-31)

Source: the same evaluation package after its 2026-08-31 multi-lens audit (`docs/LIMITATIONS.md`
R11–R17 there; `governor/harness.js`, `governor/gate.js`). §4.2 above records that the rungs have one
meaning upstream. This section writes down the semantics the package settled on, tested, and ran
against the shipped gate, so that when the `HumanApprovalPort` of §4.2 is built it implements a
known contract rather than a fresh interpretation. Everything stays opt-in / default-OFF.

### 5.1 The contract (what each rung authorises, everywhere)

| Rung | Who decides | What the actuation layer does |
|---|---|---|
| `allow` | nobody — automatic | runs as proposed |
| `degrade` | automatic | runs in **reduced** form (the adapter defines "reduced": smaller model via `routeModel`, fewer steps, deferred to a cleaner/cheaper slot) — never silently identical to `allow` |
| `escalate` | a human | runs **only** with an explicit approval object; otherwise nothing runs |
| `block` | a human, and only for a fallback | the action as proposed never runs; a human may authorise the reduced/deferred **fallback** and nothing else |
| `terminate` | nobody can | never runs — not with an approval, not with any approval; checked **first**, before any approval object is inspected |

Reference actuation function (44 lines, imports nothing, property-tested over 4,100 cases upstream
of us): `execute(decision, task, approval)` → refuse `terminate` first; auto-run `allow`/`degrade`;
run `escalate`/`block` only when `approval.approved === true`; anything else refused with a reason.
An action **not on the ladder** is treated exactly like `block` (runs only with approval) — the same
rank `severityOf()` gives an unknown verdict — never like `allow`.

### 5.2 What this changes in kaiban-distributed (all additive)

- **`shared/admission-gate.ts`** must stop collapsing the top three rungs: `escalate` → the
  `HumanApprovalPort` (§4.2); `block` → the port, but the only thing it may return is a fallback
  task; `terminate` → never routed anywhere (DLQ with `terminated_by_gate`). Today all three are one
  DLQ outcome — the ladder's authority half is lost at the last hop.
- **Fail-closed re-aggregation includes the decision's own action.** When normalising an off-ladder
  verdict (§4.1) also fold `decision.action` itself into the most-severe set; with the shipped gate it
  is always one of the verdict actions, but a foreign gate object with an off-ladder action and no
  verdicts would otherwise resolve to `allow`.
- **A fifth port: metering.** The gate reasons about an *estimate* the acting agent declares
  (`GateContext.estimatedCostUnits`, or a carbon estimate in the package). The four ports — signal,
  forecast, human, actuation — name no source of the *actual* consumption that budget accounting
  (`commit()`) needs. Add a `MeteringPort` (trusted post-execution measurement: tokens from the
  provider response, cost from `priceUsage`, energy/carbon when a metric exists) and make budgets
  reconcile estimate against metered actual. Without it, an under-declaring agent is `allow`ed and
  monotonicity is no defence — the estimate is attacker-controlled input (evaluation limitation R15).
- **`executedAt` and lifecycle records in the audit log** (extends §4.4): an audit record is written at
  decision time; actuation may happen later (deferral, approval latency, a paused task — §6 below).
  Record `executedAt` separately, and admit a second record kind — lifecycle/control events — into the
  same hash chain so "who approved / paused / stopped what, when" is in one tamper-evident trail.
- **Anchor hygiene** (extends §4.3): `anchor()` should return `{length, tipHash, anchorHash}` where
  the third is a digest of the first two, and `verify(anchor)` should check it (a corrupted anchor
  object is otherwise indistinguishable from a broken chain); document that an anchor protects only
  the anchored prefix — a tail rewritten and re-hashed after it passes both checks — so anchors are
  taken after every batch that matters.
- **`degrade` needs a distinct physical meaning per adapter or it does no work.** Measured in the
  package's charging scenario: because `allow`/`degrade`/`escalate` all produced the same action and
  `block`/`terminate` fell back to the unmanaged default, the gate could only *subtract* from the
  outcome (R13). When wiring `degrade` → `routeModel` (§4.2c) make the reduced form observable in the
  audit record (`degradedTo: <model|steps|slot>`).
- **Docs:** `docs/governance/GOVERNANCE.md` gains the table above verbatim, plus the two rules that
  most surprised readers of the package: *human decisions = every `escalate` + every `block`* (that
  is the number an operator staffs for), and *"paused" is neither refused nor stopped* — a paused
  task is gated once, when it arrives, and simply runs later on that audited decision.

## 6. HITL lifecycle controls — STOP / PAUSE / RESUME for workflows, tasks and agents (ADR-025 / ADR-026, planned)

> **New workstream, nothing like it exists today.** A human at the board must be able to **stop**,
> **pause** and **resume** (a) a whole workflow, (b) one task, (c) one agent — including an agent
> that is in the middle of an LLM call or other automation — and have every layer honour it
> cooperatively, checkpointing on pause and rehydrating on resume. Opt-in / default-OFF
> (`CONTROL_PLANE_ENABLED`), additive, and it needs an ADR because it adds a channel.

### 6.1 Discovery — what v2.0 has, and what is missing

**What exists and is reused (verified against the code):**
- **One `AbortController` per task** in `AgentActor.executeTask` (ADR-014), merged into every
  LangChain `.invoke`/`.stream` by `buildOwnedLlm` (`owned-llm.ts`). Aborting it stops the provider
  request and the token spend — this is the interruption point STOP needs, and it works **mid-LLM
  call** for the OpenAI-compatible provider path.
- `CompletionRouter.wait(taskId, timeoutMs, label, signal?)` already accepts a signal and cleans up.
- `WorkflowOrchestrator` + `CheckpointStore` (ADR-018): per-completed-step `{taskId, result}` in Redis
  (`kaiban-orchestrator:checkpoint:<workflowId>`, 24 h TTL); a fresh process with the same
  `workflowId` resumes past cached steps (`isResuming()`).
- `gracefulShutdown({deadlineMs, steps})` — an ordered, deadline-bounded drain; SIGTERM already
  aborts in-flight controllers via `AgentActor.stop()`.
- **The HITL delivery pattern** in `SocketGateway`: `socket.on('hitl:decision')` → validate →
  `wrapSigned` → `LPUSH kaiban-hitl-decisions:<taskId>` (300 s) **and** `PUBLISH
  kaiban-hitl-decisions` → ACK. Dual delivery = a late subscriber still finds the decision.
- `AgentRegistry` kill-switch (`revoke()` ⇒ `terminate`), `ActionGate` + `AuditLog`, and the
  `IAdmissionGate` port the actor consults before running anything.
- BullMQ `Worker.pause()/resume()` and KafkaJS `consumer.pause()/resume()` exist in both real drivers
  (not surfaced by `IMessagingDriver` yet).

**What is missing (the gaps this workstream closes):**
1. **No control plane.** No control channel, no command message type (`MessagePayload` has no
   `type` discriminator), no board→runtime path except `hitl:decision`, no HTTP control route.
2. **No way to reach a running agent.** Mailboxes are point-to-point competing-consumer queues;
   workers subscribe to **zero** Redis Pub/Sub channels (`AgentStatePublisher` is publish-only). The
   Kafka driver refuses a second `subscribe()`.
3. **Cancellation is not addressable.** `inFlight` is a `Set<AbortController>` — the `taskId`
   association is lost; only `stop()` (abort all + unsubscribe) and the timeout can fire it.
4. **Abort is destructive.** An aborted handler rejects → counts as a retry → after 3 attempts lands
   in the DLQ as a failure. There is no "paused: do not retry, do not DLQ" outcome and nothing is
   saved when the abort fires; the board would show agent `ERROR` + task `BLOCKED`.
5. **Mid-call abort is provider-scoped** (ADR-014) and **partial LLM output is never captured**.
6. **Checkpoints are coarse**: completed steps only — no in-flight step state, no agent memory, no
   pause marker, no HITL cursor. Workflow status has no core type (board-side union + loose strings).
7. **No PAUSED / STOPPING / STOPPED states** in `TaskStatus` / `AgentStatus`; `SocketGateway.
   applyStatusUpdate` clears tasks when `RUNNING` follows a terminal status.
8. **The kill-switch is in-memory, per-process, not wired, and irreversible** (`revoke` → only
   `register` un-revokes, resetting counts). No reversible *suspend*.
9. **HITL is per-`taskId`, one-shot, three-valued**; there is no workflow-scope command and the
   orchestrator holds no handle a supervisor could signal (`memoize`/`runStep` take an optional
   signal that no example ever constructs).
10. **Board authz is env-gated** (`BOARD_JWT_SECRET` unset ⇒ anonymous). HITL tolerates that; a
    destructive STOP must not.

### 6.2 Semantics (the spec, EARS form)

Scopes: `workflow` (by `workflowId`), `task` (by `taskId`), `agent` (by `agentId`). Commands:
`STOP`, `PAUSE`, `RESUME`. Every command carries a `commandId`, `issuedBy`, `issuedAt`, `reason?`.

| Command | Meaning | Resumable | Terminal state |
|---|---|---|---|
| **STOP** | interrupt now; discard in-flight work; **no retry, no DLQ-as-failure**; release budget reservations | no | task `STOPPED`, agent `IDLE`, workflow `STOPPED` |
| **PAUSE** | reach a safe point (or interrupt), **save state**, hold; nothing new is admitted | yes | task `PAUSED`, agent `PAUSED`, workflow `PAUSED` |
| **RESUME** | rehydrate the saved state and continue from the last checkpoint | — | back to `DOING` / `EXECUTING` / `RUNNING` |

- **C-1** WHEN an operator issues `STOP` for scope *S*, the runtime SHALL abort every in-flight
  handler in *S* within `CONTROL_ACK_DEADLINE_MS` (default 5 000), SHALL NOT retry or dead-letter the
  aborted tasks as failures, and SHALL publish their status as `STOPPED` with the `commandId`.
- **C-2** WHEN an operator issues `PAUSE` for *S*, each agent in *S* SHALL stop admitting new tasks,
  SHALL checkpoint each in-flight task (payload, attempt, `startedAt`, step cursor, partial output if
  any) to the `TaskCheckpointStore`, THEN SHALL abort the in-flight handler with abort reason
  `paused`, and SHALL publish `PAUSED`.
- **C-3** WHEN an operator issues `RESUME` for *S* and a checkpoint exists, the runtime SHALL
  re-dispatch each paused task **with the same `taskId`** carrying `resumeOf: <checkpointRef>`, and
  the receiving actor SHALL treat a `taskId` it holds a checkpoint for as a resume, never as a
  duplicate (the `taskId`-dedup invariant is what makes this safe).
- **C-4** WHILE an agent is `PAUSED`, its admission gate SHALL refuse every task with reason
  `agent_paused` **without consuming it** (the mailbox is paused at the driver, so the task waits in
  the queue rather than being dead-lettered).
- **C-5** IF a `PAUSE` cannot reach a safe point before `CONTROL_ACK_DEADLINE_MS`, THEN the actor
  SHALL abort anyway, checkpoint what it has (step cursor + partial output), and mark the checkpoint
  `interrupted: true` so RESUME re-runs the interrupted step from its start.
- **C-6** Every command SHALL be idempotent: a `PAUSE` on an already-paused target, a `RESUME` on a
  running target, or a repeated `commandId` SHALL produce a `noop` acknowledgement and no state change.
- **C-7** Every node that receives a command SHALL acknowledge it (`applied | noop | refused |
  timeout`) on the state channel; the board SHALL show a target as *pending* until acknowledged and
  as *unconfirmed* after the deadline — a lost command is visible, never silent.
- **C-8** Every command SHALL be authenticated (JWT — `BOARD_JWT_SECRET` becomes **required** when
  `CONTROL_PLANE_ENABLED`; anonymous control is refused, fail-closed), authorised by the Action Gate
  under a new operation `lifecycle-control` (policy-as-code decides who may stop/pause what), and
  appended to the audit chain as a lifecycle record with `executedAt` filled in when the ack arrives.
- **C-9** `STOP` SHALL win over `PAUSE`, and either SHALL win over `RESUME`, when commands for the
  same target overlap; ordering is by `issuedAt` with `commandId` as tiebreak.
- **C-10** `STOP` / `PAUSE` of a workflow SHALL be owned by the orchestrator (it is the only writer
  of `teamWorkflowStatus`, invariant I4); agents never set workflow status, they only report their
  own task/agent states.
- **C-11** WHEN the process receives SIGTERM, the graceful-shutdown drain SHALL behave as an implicit
  `PAUSE` of every in-flight task (checkpoint, then abort), so a redeploy is resumable.
- **C-12** IF the LLM provider path cannot be aborted (non-OpenAI-compatible, ADR-014 limitation),
  THEN `PAUSE`/`STOP` SHALL take effect at the next step boundary (the handler polls `isPaused()`)
  and the actor SHALL report `outcome: deferred-to-step-boundary` in the ack.
- **C-13** Partial LLM output captured at a pause SHALL be stored under the same PII sanitisation and
  size caps as any result (`sanitizeDelta`, 20 KB), and SHALL be offered to the resumed step only as
  optional context — never spliced into a "resumed generation".

### 6.3 Architecture — layer by layer

**(a) Control channel — `kaiban-control` (the sixth canonical channel; ADR-025).** Redis Pub/Sub,
pinned regardless of `MESSAGING_DRIVER` exactly like state and HITL (invariant I5): broadcast is
what a control plane needs and the durable brokers only offer competing consumers. Messages are
`wrapSigned` (`CHANNEL_SIGNING_SECRET`). Dual delivery as for HITL: `PUBLISH kaiban-control` **and**
`LPUSH kaiban-control:<scope>:<targetId>` (TTL 300 s) so a node that subscribes late — or a paused
agent's fresh process — can catch up on `subscribe`. Message shape (CloudEvents-aligned so it drops
into §3's envelope as `type: com.kaiban.control.<command>`):
```jsonc
{ "commandId": "<uuid>", "issuedAt": "…Z", "issuedBy": "<subject from JWT>",
  "scope": "workflow" | "task" | "agent", "targetId": "<workflowId|taskId|agentId>",
  "command": "STOP" | "PAUSE" | "RESUME", "reason": "operator note",
  "deadlineMs": 5000, "traceHeaders": { "traceparent": "…" } }
```
Acks travel on the existing state channel as a `control` delta (`{ commandId, nodeId, agentId?,
taskId?, outcome, at }`) — no seventh channel; the board already consumes that stream.

**(b) Board (`board/`).** `WorkflowBanner` gains **Stop / Pause / Resume** for the workflow (with a
confirm dialog for Stop; Resume only shown when `PAUSED`); `TaskCard`/`TaskDetailModal` gain Stop /
Pause / Resume for one task; `AgentCard` gains Pause / Resume / Stop for one agent (Stop = abort its
current task and pause its mailbox). `socketClient.sendControlCommand(cmd)` emits `control:command`
with an 8 s ACK; `boardStore` tracks `pendingCommands` by `commandId` and renders *pending* →
*applied* / *unconfirmed*; new badges/columns for `PAUSED` and `STOPPED`; `applyDelta` must not
clear tasks when `RUNNING` follows `PAUSED` (only after a terminal status). a11y: buttons are real
`<button>`s with `aria-pressed`/`aria-busy`; Playwright baselines extended.

**(c) Gateway (`SocketGateway`, `GatewayApp`).** New socket event `control:command` and, for
automation parity, `POST /control/commands` (same handler). Pipeline: zod-validate the command →
authenticate (JWT required; refuse otherwise) → `ActionGate.evaluate({ operation:
"lifecycle-control", agentId: issuedBy, payload: cmd })` (policy rules such as *only role
`operator` may STOP a workflow*, *agents may not stop each other*) → `AuditLog.append` (lifecycle
record) → `wrapSigned` → dual delivery → ACK `{ ok, commandId }` → publish a `control` metadata delta
so every connected board sees the command was issued. The gateway keeps a small `CommandLedger`
(`commandId` → acks received) to surface *unconfirmed* after `deadlineMs` and to answer `GET
/control/commands/:id`.

**(d) Worker / agent node (`agent-node.ts`, `AgentActor`).**
- New `ControlSubscriber` (Redis Pub/Sub on `kaiban-control`, `unwrapVerified`, scope filter:
  `agent` = my `agentId`, `task` = a `taskId` I hold, `workflow` = a `workflowId` carried in the
  task payload — `dispatchToAgent` gains an optional `workflowId` so agents know which workflow a
  task belongs to). On subscribe it drains the `LPUSH` catch-up list for its own scope keys.
- `AgentActor` API (additive): `inFlight: Map<taskId, InFlightTask{ controller, startedAt, attempt,
  payload, cursor?, partial? }>`; `stopTask(taskId, cmd)`, `pauseTask(taskId, cmd)`, `pauseAll(cmd)`,
  `resumeAll(cmd)`, `isPaused()`. Abort reasons become typed: `controller.abort(new
  ControlAbort("stopped" | "paused", commandId))`. `executeWithRetries` inspects
  `signal.reason`: a `ControlAbort` is **neither retried nor dead-lettered**; the task is published
  as `STOPPED` (with a `stopped_by_operator` record on the failed channel so `CompletionRouter`
  waiters resolve with a reason) or `PAUSED` (nothing on completed/failed — the task is still owned).
- **Admission hold:** `IMessagingDriver` gains optional `pause()` / `resume()` (BullMQ
  `Worker.pause(true)` / Kafka `consumer.pause([{topic}])`), so a paused agent stops *taking* work
  while the queue keeps it; `IAdmissionGate` (already consulted first) refuses with `agent_paused`
  as the belt to that brace.
- **Safe points:** `TaskHandler` gains a third argument `ControlContext { signal, isPaused(),
  checkpoint(partial: TaskCheckpointPartial), onPause(cb) }`. The KaibanJS bridge calls
  `checkpoint()` at each step boundary it can observe (task start/end events from the team's store
  subscription) and honours `isPaused()` between steps — the fallback for non-abortable provider
  paths (C-12).
- **`TaskCheckpointStore`** (Redis `kaiban-task-checkpoint:<taskId>`, TTL configurable, default
  24 h — same TTL discipline as the orchestrator store): `{ taskId, agentId, workflowId?, payload,
  attempt, startedAt, pausedAt, commandId, cursor?, partialOutput?, interrupted }`. `RESUME`
  re-dispatches the original payload with `resumeOf` set; the actor loads the checkpoint, passes
  `cursor`/`partialOutput` in the `ControlContext`, and clears the checkpoint on completion.
- Graceful shutdown's *stop-actor* step becomes *pause-all-then-stop* when the control plane is
  enabled (C-11).

**(e) LLM layer (`kaiban-agent-bridge.ts`, `owned-llm.ts`).** The owned instance already merges
the actor signal; add a `PartialOutputBuffer` on the `.stream` wrapper that accumulates chunks so a
pause mid-generation preserves what was produced (sanitised, capped) as `partialOutput`. Document —
as ADR-014 does — that KaibanJS `team.start()` takes no signal and non-OpenAI providers pause at the
next step boundary. No KaibanJS fork.

**(f) Orchestrator (`shared/orchestrator.ts`).** `WorkflowOrchestrator` gains `control:
WorkflowControl` — its own `ControlSubscriber` for `workflowId` plus one `AbortController` for the
run. `runStep`/`memoize` pass that signal to `router.wait` (already supported) and to
`waitForHITLDecision` (needs a `signal` parameter — a workflow paused while `AWAITING_VALIDATION`
must stop waiting). On `PAUSE`: write `__control: { state: "PAUSED", at, by, commandId, step }`
into the checkpoint, abort the current wait, fan out `task`-scope `PAUSE` for the step's in-flight
`taskId`s (or rely on the broadcast `workflow` scope — both are delivered), publish
`teamWorkflowStatus: PAUSED` (orchestrator-owned), and either park or exit. On `RESUME`: the
existing resume path (`isResuming()`) skips cached steps; the interrupted step is not cached so it
re-runs, and its tasks resume from their own checkpoints. On `STOP`: `__control.state = STOPPED`,
abort, publish `STOPPED`; the checkpoint is kept (audit) until TTL. A `WorkflowStatus` core type
finally lands in `src/domain/entities` (`RUNNING | PAUSED | STOPPED | FINISHED | ERRORED |
BLOCKED`) and the board type imports it instead of duplicating it (ADR-026).

**(g) Governance and audit.** `GateOperation` gains `lifecycle-control` (policy-as-code decides
who may do what to which scope); `AuditLog` accepts a lifecycle record kind in the same chain with
`executedAt` (§4.4, §5.2); `AgentRegistry` gains a reversible **`suspend(agentId) / unsuspend`**
distinct from `revoke` — an agent-scope `PAUSE` suspends it so its own kill-switch validator
returns `block` while paused, and `RESUME` un-suspends without resetting invocation counts.
Registry state moves to Redis when the control plane is on, so a suspended agent stays suspended
across a restart. `docs/COMPLIANCE.md` Art. 14 (human oversight) turns from 🟡 to ✅ on this.

**(h) Federation parity.** A2A `tasks/cancel` maps onto `STOP(task)` and reports `canceled`; an
optional MCP tool `control_task` exposes the same three commands behind the existing elicitation
consent gate; the AgentCard advertises a `lifecycleControl` capability.

### 6.4 State machines (additive members only)

- `TaskStatus`: `TODO | DOING | AWAITING_VALIDATION | DONE | BLOCKED` **+ `PAUSED` + `STOPPED`**
  — `DOING → PAUSED → DOING` (resume), `DOING|PAUSED|AWAITING_VALIDATION → STOPPED` (terminal).
- `AgentStatus`: `IDLE | THINKING | EXECUTING | ERROR` **+ `PAUSED`** (+ transient `STOPPING`
  while the ack deadline runs).
- `WorkflowStatus` (new core type): `RUNNING → PAUSED → RUNNING`, `RUNNING|PAUSED → STOPPED`.
- `SocketGateway.applyStatusUpdate` / `boardStore.applyDelta`: clear tasks only after `FINISHED |
  STOPPED | ERRORED`, never after `PAUSED`.

### 6.5 Sequences

1. **Workflow PAUSE.** Board → `control:command{scope: workflow}` → gateway: auth → gate → audit →
   `PUBLISH kaiban-control` + `LPUSH` → ACK. Orchestrator: writes `__control PAUSED`, aborts its
   wait, publishes `teamWorkflowStatus: PAUSED`. Each worker holding a task of that workflow:
   `driver.pause()`, `checkpoint()`, `controller.abort(ControlAbort("paused"))` → handler rejects →
   actor sees the reason → no retry, no DLQ → publishes task `PAUSED`, agent `PAUSED`, and a
   `control` ack. Board turns the pending badge into *paused* per target.
2. **Task STOP mid-LLM call.** Same ingress with `scope: task`. The one worker holding `taskId`
   aborts its controller; `owned-llm`'s merged signal cancels the provider request (token spend
   stops); actor publishes task `STOPPED` + a `stopped_by_operator` record on the failed channel;
   `CompletionRouter` resolves the orchestrator's `wait` with that reason; orchestrator decides
   (skip / substitute / stop workflow) per its own policy; budget reservation released.
3. **RESUME.** Ingress as above. Orchestrator (new or same process) resumes via `isResuming()`;
   worker `driver.resume()`, `unsuspend`; for each checkpoint in scope the orchestrator (or the
   node's `ControlSubscriber`, for agent scope) re-dispatches the payload with `resumeOf`; the actor
   recognises the held `taskId`, loads the checkpoint, runs the handler with `cursor`/`partialOutput`
   in its `ControlContext`, publishes `DOING`/`EXECUTING`, clears the checkpoint on completion.

### 6.6 Failure modes and the guarantee each one gets

| Situation | Behaviour |
|---|---|
| Command published while a node is down / not yet subscribed | `LPUSH` catch-up list (300 s) is drained on subscribe; beyond that the board shows *unconfirmed* and the operator re-issues (idempotent) |
| Node dies between checkpoint and ack | checkpoint is durable; the task is `PAUSED` in Redis; next `RESUME` re-dispatches; the board shows *unconfirmed* for that target |
| Duplicate / out-of-order commands | `commandId` ledger + C-9 precedence; every repeat is a `noop` ack |
| `PAUSE` during retry back-off | back-off timer is cancelled; attempt count is checkpointed; resume continues at the same attempt |
| `PAUSE` while `AWAITING_VALIDATION` | `waitForHITLDecision` aborts on the workflow signal; the HITL cursor is checkpointed; on resume the same `taskId` list/pub-sub race re-arms |
| Non-abortable provider path (ADR-014) | takes effect at the next step boundary; ack says `deferred-to-step-boundary`; hard timeout still fires |
| Control plane disabled | no subscriber, no route, no event: behaviour identical to v2.0 (default-OFF) |
| Auth not configured | control refused, fail-closed; HITL editorial gate unaffected |

### 6.8 Decisions to settle first
- **Sixth channel vs. multiplexing on `kaiban-hitl-decisions`.** A separate channel keeps HITL's
  three-valued contract untouched and lets policy differ (recommended); multiplexing avoids a
  channel-contract change but couples two semantics. Either way: ADR-025.
- **Where RESUME re-dispatch originates** — the orchestrator (knows the workflow) vs. the node's
  `ControlSubscriber` (knows its checkpoints). Proposal: agent/task scope → the node; workflow scope
  → the orchestrator; both idempotent by `taskId`.
- **Checkpoint TTL and retention** after `STOP` (audit value vs. Redis footprint).
- **Partial output**: keep (context on resume) or drop (simplest, no PII surface). Default: keep,
  sanitised, capped, off unless `CONTROL_KEEP_PARTIAL_OUTPUT=true`.
- **Kafka**: the single-subscription driver limit means the control subscriber is always a Redis
  Pub/Sub client, even on Kafka deployments — consistent with I5, but it makes Redis a hard
  dependency of the control plane. Accept, or add a Kafka control topic later.
- **Should `PAUSE` of an agent also pause tasks it has already handed off?** No — scope is literal;
  workflow scope exists for the cascading case.
