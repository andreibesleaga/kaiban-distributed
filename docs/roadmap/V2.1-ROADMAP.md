# kaiban-distributed — v2.1 Roadmap (post-2.0 plan)

> **Status: PLAN (not implemented).** Saved for a later version. v2.0 ships the items in
> `KAIBAN-v2.0-MASTER-PLAN.md`; this document captures the next tranche deferred during BETA.3.
> Authoritative invariants/NFRs still apply (master plan §B1). Everything here stays **opt-in /
> default-OFF** (invariant #8) and additive (no breaking change to the 5 canonical channels without an ADR).

Three workstreams:
1. **Federation-egress enforcement** — extend the Action Gate to outbound A2A / MCP traffic.
2. **Default-wire the fleet cost limiter** — make economics enforcement turnkey (Redis-backed) without
   forcing each consumer to inject a limiter.
3. **Universal agent messaging schema** — a driver-agnostic, schema-enforced envelope for ALL agent
   pub/sub (Kafka, Redis, BullMQ, future AMQP), with a flexible payload per message type. **(centerpiece)**

---

## 1. Federation-egress enforcement (ADR-022, planned)

**Today (v2.0):** the Action Gate (`src/governance/action-gate.ts`) is enforced on the **inbound** task
hot path (`AgentActor` pre-execution guard, ADR-021). **Outbound** federation — the gateway dispatching
A2A `message/send` (`KaibanAgentExecutor`) and the MCP server's `dispatch_task` — is NOT yet gated.

**Goal:** every *outbound* / cross-boundary action also passes the gate, so policy / kill-switch / cost
apply symmetrically to what agents emit, not just what they receive.

**Design (additive, default-OFF):**
- Introduce an `EgressGate` adapter (reusing `IAdmissionGate` / `buildAdmissionGate`) that wraps the
  same `ActionGate`. Operations: `outbound-message` (A2A) and `tool-call` (MCP `dispatch_task`).
- **A2A:** in `KaibanAgentExecutor.execute` (`a2a-executor.ts`), call the gate **before** publishing to
  the agent mailbox; a `block`/`terminate` becomes a terminal A2A `rejected` task (no publish), `degrade`
  annotates the task. Reuses the existing `validateTaskInput` path.
- **MCP:** in the `dispatch_task` tool handler (`mcp-server.ts`), call the gate before `deps.dispatchTask`
  — composes with (does not replace) the existing elicitation consent gate.
- Wire via the gateway composition (`main/gateway.ts`) behind `GOVERNANCE_ENABLED`, sharing one
  `ActionGate` + `AuditLog` instance with the worker config.
- **Checks:** gate block→A2A `rejected` / MCP error result (no side effect); audit records the egress
  decision; default-OFF preserves current behavior; A2A + MCP conformance suites stay green.

## 2. Default-wire the fleet cost limiter (ADR-023, planned)

**Today (v2.0):** `CostReservation` / `RateCostLimiter` exist and are 100%-tested; the worker admission
gate adds cost enforcement **only when a `CostLimiterPort` is injected** (`buildWorkerAdmissionGate`), so
out-of-the-box `ECONOMICS_ENABLED` does not yet enforce a *fleet* budget — by design, to avoid forcing a
Redis client into every node and to keep budgets fleet-wide rather than per-node.

**Goal:** when `ECONOMICS_ENABLED=true`, the worker automatically builds a **Redis-backed**
`RateCostLimiter` (shared fleet state) and composes it into the admission gate — turnkey fleet cost
control — while keeping a `RateLimiterMemory` fallback for single-node / test.

**Design (additive, default-OFF):**
- A `buildFleetCostLimiter(economics, { redisUrl, redisTls })` factory in `src/shared` returning a
  `RateCostLimiter` whose `RateLimiterFactory` constructs `RateLimiterRedis({ storeClient, … })` (shared
  ioredis client; reuses the node's existing Redis config + TLS). Memory fallback when `redisUrl` absent.
- `buildSecurityDeps` / `agent-node.ts` pass it into `buildWorkerAdmissionGate` when `ECONOMICS_ENABLED`.
- Lifecycle: the limiter's Redis client joins the node's graceful-shutdown step list.
- **Decisions to settle:** cost-unit definition (micro-USD vs tokens) and where the per-step
  `estimatedCostUnits` comes from (model pricing table via `cache-accounting` / `model-router` →
  `GateContext.estimatedCostUnits`). Likely a small `estimateCost(payload, pricing)` helper.
- **Checks:** two nodes share one budget (fleet-wide reservation/compensation across processes, real
  Redis e2e); disabled ⇒ no limiter, no Redis client; per-task accounting unchanged (§B1.3 COST guard).

## 3. Universal agent messaging schema (ADR-024, planned) — **centerpiece**

### Problem
Agents publish to several backends (Redis Pub/Sub, BullMQ/Redis streams, Kafka; future AMQP) over the 5
canonical channels. Today the wire shape is the internal `MessagePayload`
(`{ taskId, agentId, data, timestamp, traceHeaders? }`) — adequate, but **not a formally-specified,
versioned, schema-enforced contract**, and not described in a machine-readable, tooling-friendly way. We
want ONE generic, driver-agnostic envelope that any agent (any specialization, any framework) can publish
and any consumer can validate, **with the body staying flexible** per message type / task.

### Research outcome (industry standards, verified 2026)
- **CloudEvents 1.0.2 (CNCF)** — a *protocol-agnostic* event **envelope**: standard metadata attributes
  (`id`, `source`, `type`, `specversion`, `time`, `subject`, `datacontenttype`, `dataschema`, + named
  **extension attributes**) wrapping a flexible `data` payload. Has official **bindings** for Kafka
  (structured + binary content modes; non-data attributes → `ce_`-prefixed headers), AMQP, MQTT, NATS,
  HTTP, WebSockets. This is exactly the "generic header + message" the envelope needs.
- **AsyncAPI 3.x** — the "**OpenAPI for event-driven / message-driven APIs**": one YAML/JSON document
  describing every **channel**, **message**, **payload schema** (AsyncAPI Schema = JSON-Schema superset,
  or **Avro**), **operation** (send/receive), **server**, and **protocol binding** (Kafka/AMQP/MQTT/NATS/
  WS). This is the *contract & enforcement spec* layer + a tooling/codegen/validation ecosystem.
- **Schema enforcement** — JSON Schema (default; matches our `zod` + `fast-check` stack) or Avro/Protobuf
  via a **Schema Registry** (Confluent-compatible) for Kafka; for Redis/BullMQ we validate in-process at
  publish/consume.

### Proposed design: a CloudEvents envelope, an AsyncAPI contract, driver-agnostic enforcement
**(a) The envelope — CloudEvents-aligned `KaibanEvent`** (supersedes the raw `MessagePayload` on the wire;
`MessagePayload` becomes the `data` body):
```jsonc
{
  "specversion": "1.0",
  "id": "<uuid>",                         // unique event id
  "source": "kaiban/agent/<agentId>",      // producer
  "type": "com.kaiban.task.dispatch",      // versioned event type (registry key)
  "time": "2026-…Z",
  "datacontenttype": "application/json",
  "dataschema": "kaiban://schemas/task.dispatch/1",  // → schema registry entry
  // kaiban extension attributes (CloudEvents extensions — flat, string-ish):
  "taskid": "<taskId>",                    // dedup key (invariant: AP+BASE)
  "agentid": "<targetAgentId>",
  "tenantid": "<tenant>",                  // optional
  "traceparent": "…", "tracestate": "…",   // W3C trace context (replaces traceHeaders)
  // flexible, per-type body — validated against `dataschema`:
  "data": { /* task/message/state-event payload, specialization-specific */ }
}
```
**(b) The contract — `asyncapi.yaml`** describing the 5 canonical channels
(`kaiban-agents-{id}`, `kaiban-events-completed`, `kaiban-events-failed`, `kaiban-state-events`,
`kaiban-hitl-decisions`), each message = the `KaibanEvent` envelope with a per-`type` payload schema, plus
Kafka/Redis bindings. Generated docs + types; lints in CI (AsyncAPI CLI validator).
**(c) Enforcement — a schema layer in the Messaging Abstraction Layer (MAL):**
- A `SchemaRegistry` (start with an in-repo JSON-Schema map keyed by `type`+version; Confluent-registry
  adapter optional for Kafka) + an `EnvelopeCodec` that wraps/validates on `publish` and parses/validates
  on `subscribe`, in **every** driver (BullMQ/Kafka/AMQP) — so enforcement is uniform regardless of
  `MESSAGING_DRIVER`. Invalid envelope/payload → reject before publish (mirrors `A2A_INPUT_CAPS`), or
  route to DLQ on consume (`schema_violation`).
- **Backward-compatible migration:** a transitional decoder accepts both raw `MessagePayload` and the new
  `KaibanEvent` (detect `specversion`), so a mixed fleet interoperates during rollout; envelope becomes
  mandatory in a later major. Body stays flexible — only the envelope + the named `type`'s schema are
  enforced.
- **Versioning & evolution:** `type` carries a version suffix; schema changes follow compat rules
  (backward/forward) per `event-governance` skill; registry is the source of truth.

### Why this shape
- **Generic + flexible:** CloudEvents standardizes only the envelope; `data` is whatever the agent's
  specialization/task needs — enforced *per `type`*, not globally.
- **Driver-agnostic:** CloudEvents has bindings for every backend we use/plan; the MAL codec hides the
  per-driver header/value mapping (Kafka `ce_` headers vs Redis JSON).
- **Tooling:** AsyncAPI gives machine-readable docs, codegen, contract tests, and the "Kafka-OpenAPI"
  experience the maintainer asked for; JSON Schema reuses our existing `zod`/`fast-check` validation.
- **Interop:** CloudEvents/AsyncAPI are CNCF/Linux-Foundation standards → external agents & tools can
  speak our channels without bespoke glue; complements A2A (front door) + MCP (tool surface).

### Phased delivery (v2.1)
- **M-Schema.1** — define `KaibanEvent` (CloudEvents) types + the in-repo JSON-Schema registry +
  `EnvelopeCodec` (publish/consume validation) as a MAL add-on; **off by default** behind
  `MESSAGING_SCHEMA_ENFORCED`. Transitional dual-decoder. 100% cov.
- **M-Schema.2** — author `asyncapi.yaml` for the 5 channels + CI lint (AsyncAPI CLI) + generated docs.
- **M-Schema.3** — Kafka Schema-Registry adapter (Confluent-compatible) + structured/binary content-mode
  mapping; Redis/BullMQ in-process validation; `schema_violation` DLQ taxonomy entry.
- **M-Schema.4** — flip enforcement on by default in a later **major** (with MIGRATION); keep the
  dual-decoder one version for rollout.

### Risks / decisions to settle first
- Changing the wire envelope touches the **messaging-channel contract** → requires an ADR + careful
  migration (§6 forbidden-actions / §B1.2). Dual-decoder + default-off de-risks rollout.
- Cost-unit + pricing source overlaps with workstream 2 — settle once.
- Avro-vs-JSON-Schema default: start JSON Schema (matches `zod`); offer Avro for Kafka-registry users.

## Consistency-review findings (deferred to v2.1+)

> Recorded during the final v2.0 plan ↔ code ↔ docs consistency review (2026-06). These are
> **genuine deferrals** — features the master plan describes but that v2.0 ships as a *seam / flag /
> verification-process* rather than a full implementation. They are intentionally out of v2.0 scope;
> captured here so nothing is silently dropped. All remain opt-in / default-OFF and additive (no
> change to the 5 canonical channels without an ADR). Verified against the v2.0 (`feat/v2.0`) code.

### CR-1. A2A forward-compat — advertised-but-not-served / flagged-only (Phase A finish)
The v2.0 A2A surface is stable v0.3 with a v1.0 seam; several "Phase A" forward-compat items are
declared on the AgentCard (the seam) but not yet implemented behind it:
- **gRPC transport** — advertised in `additionalInterfaces` (`a2a-agent-card.ts`, `${baseUrl}/a2a/grpc`)
  but **only JSON-RPC at `/a2a/rpc` is actually served**; no gRPC server. → implement the gRPC binding.
- **Push-notification webhooks** — the `pushNotifications` capability flag is wired end-to-end, but
  there is **no webhook delivery** implementation. → implement delivery + signing.
- **Signed-AgentCard (JWS) verify** — **absent**; the card is plain JSON (JWT request-auth is separate).
  → add JWS card signing + verification (flagged).
- **Lifecycle states `input-required` / `auth-required`** — **absent** (only `rejected` of the extended
  set is emitted, alongside `submitted/working/completed/failed/canceled`). → add the remaining states.

### CR-2. Resilience (Phase R) — supervision & loop-guard completeness
- **Auto-revival supervisor with backoff+jitter** — **absent** as code; v2.0 resilience leans on message
  durability + let-it-crash + checkpoint/resume + platform (k8s) restart. → add an in-process supervised
  auto-revival path (actor-revival only) with backoff+jitter.
- **Loop-termination guards** — iteration cap (`maxIterations`) and token-budget cap are present, but
  **wall-clock cap and oscillation detection are absent**. → add wall-clock + oscillation/handoff guards.
- **Circuit-breaker half-open** — `SlidingWindowBreaker` recovers by window expiry (auto-close), which is
  an improvement over the old time-only behavior, but it is **not a classic single-probe HALF_OPEN trial
  gate**. → add a true half-open probe if stricter recovery semantics are wanted.

### CR-3. Governance (Phase G) — provenance-check as an Action-Gate validator
The Action Gate ships firewall / breaker / cost / policy-as-code / kill-switch validators, and a
hash-chained audit log. A **dedicated provenance-check `GateValidator` is absent** — provenance/trust
lives only in the memory layer (`SecureMemoryStore` `MemoryProvenance` / trust floor), not as a gate
validator. → add a provenance validator (it is also the foundation the anti-hallucination harness below
builds on). Relatedly, federation **egress** gating remains deferred — see §1 above.

### CR-4. Evals / Observability / Guardrails stack (master plan §5 / §B5.2 / §B11.4)
The master plan's TS-native "Evals / Observability / Guardrails" stack is **documented but not present in
v2.0 code** (no deps, no CI gate). Each is honestly omitted from the v2.0 CHANGELOG/README; recorded here
so the plan↔code gap is explicit:
- **Langfuse observability** — no `@langfuse/*` dependency and no `src/infrastructure/observability/
  langfuse.ts`; observability is OpenTelemetry-only. → attach `LangfuseSpanProcessor` to the existing
  `NodeSDK` provider, env-gated (`LANGFUSE_*`), with the `sanitizeDelta` PII mask. *(Note: any doc that
  describes a "Langfuse hook" as shipped is an over-claim — see the maintainer note in the review report;
  `docs/FEATURES.md:268` should be softened to roadmap wording by its owner.)*
- **Promptfoo eval gate + trajectory evals** — no `promptfoo` dep, no `promptfooconfig.yaml`, no `eval`
  script, no CI eval step. → add the Promptfoo config (golden/edge/injection + `owasp:llm`/`owasp:agentic`
  red-team), `npm run eval`, and the CI gate; extend e2e with trajectory (outcome + required-tool) evals.
- **Zod schema-enforced agent-OUTPUT validation** — Zod is used for **input** validation (A2A/MCP) only;
  there is no `src/guardrails/` output-validation harness. → add Zod output schemas validated at each
  agent-to-agent hop (cascade guard) with bounded auto-retry.
- **Anti-hallucination runtime harness** (`src/guardrails/anti-hallucination.ts`, ADR-030) — absent;
  "anti-hallucination sign-off" in the plan is a *release verification process*, not a shipped runtime
  feature. → build the env-gated (default-off) output-grounding / self-consistency / faithfulness layer on
  top of the Action-Gate provenance validator (CR-3).

## 4. Governance findings from the external evaluation package (added 2026-08-23)

Source: `sustainability-loop-eval` v1.1.0 (github.com/andreibesleaga/sustainability-loop-eval, Zenodo
concept DOI 10.5281/zenodo.22056633), which runs architecture fitness functions through the shipped
`ActionGate` / `AuditLog` of `kaiban-distributed@2.0.0` (npm) at commit `17ad362`. Governance unit suite
71/71 and e2e 69/69 (real Redis) reproduced there. Items below are defects or gaps it surfaced; all stay
opt-in / default-OFF and additive.

### 4.1 DEFECT — off-ladder verdict can mask `terminate` (fix in v2.1, fail-closed)
`src/governance/action-gate.ts` aggregates by sorting on `GATE_ACTION_SEVERITY[verdict.action]`. An action
that is not in `GateAction` has no entry → the comparator returns `NaN` → the sort is not total and the
decision collapses to insertion order. Measured: verdicts `[allow, "not-a-rung", terminate]` → gate decision
**`allow`**; a lone rogue validator returning `"not-a-rung"` is returned verbatim. A malformed validator can
therefore outrank the kill-switch.
**Fix:** before aggregation, map any action not in the ladder to `block` (fail closed, same posture as a
throwing validator), keep the raw value in the verdict `reason`, and add unit cases: rogue-alone ⇒ `block`;
rogue + `terminate` ⇒ `terminate`; rogue + `allow` ⇒ `block`. Also export a `isGateAction()` guard.

### 4.2 GAP — the five rungs have one meaning upstream (documentation + optional human port)
In the default actor path (`shared/admission-gate.ts`) `allow`/`degrade` proceed and `escalate`/`block`/
`terminate` are treated identically (dead-letter); `degrade` degrades nothing; there is no human-approval
port; `block` vs `terminate` is undocumented (only the registry distinguishes them: revoked ⇒ `terminate`,
other inactive ⇒ `block`). The evaluation package had to define the semantics itself:
allow = run · degrade = run reduced / defer · escalate = run only with human approval · block = withheld,
human may authorise a reduced/deferred fallback only · terminate = never runs, not overridable.
**Plan:** (a) document the rung semantics and the block/terminate distinction in `docs/governance/
GOVERNANCE.md`; (b) add an optional `HumanApprovalPort` (pending-decision queue + callback, default-OFF)
consulted by the admission gate for `escalate`/`block`; `terminate` is never routed to it; (c) wire
`degrade` to `routeModel` (currently exported, never invoked) behind a flag.

### 4.3 GAP — audit log is tamper-evident for edits, not for truncation
`AuditLog.verify()` recomputes hashes but has no length/tip commitment, so tail truncation, deletion and
reordering of the last records verify as valid; `records()` returns the live internal array (callers can
mutate it). **Plan:** `anchor(): {length, tipHash}` + `verify(anchor?)`; return a frozen copy from
`records()` (or document that it is live); unit cases for truncation/deletion/reorder.

### 4.4 GAP — deferred / paused tasks have no governance notion
A verdict taken "now" that is executed later (deferral) is currently outside the gate's vocabulary; the
evaluation package gates once on arrival and executes later on that audited decision. **Plan:** record
`executedAt` on the audit record when actuation happens (separate from the decision timestamp), and point
a future pause/rehydrate of deferred work at the existing `WorkflowOrchestrator` checkpoint→resume
(`CheckpointStore`) — it is the natural place, and it is unrelated to governance today.

### 4.5 PACKAGING — export a `./governance` subpath
Importing the package root (`dist/src/index.js`) eagerly loads ~249 packages (LangChain, OTel
instrumentations, express, socket.io, ioredis, bullmq, kafkajs…). Consumers that only want the gate pay
the whole tree and inherit its advisories (21 `npm audit` findings on 2026-08-22, all transitive via
kaibanjs → LangChain/langsmith/OTel/uuid/fast-xml-parser). **Plan:** add `"./governance"` to `exports`
(gate, audit-log, policy-engine, registry, types only), and bump kaibanjs / LangChain to clear the
advisories.
